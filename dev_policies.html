DEVELOPMENT COOKBOOK

BOMO Platform Policy & Development Cookbook

Short operational policy plus implementable development rules for booking, cancellation, refunds, payouts, and video/photo reviews. Designed as a source of truth for product, backend, frontend, QA, operations, finance, and support.

No check-in/check-out dependencyNo red-flag workflowBackend state machineBOMO Collect / Property CollectAudit-ready

1. Overview

PURPOSE

Use this cookbook as the implementation reference for BOMO booking, cancellation, refund, payout, and video/photo review workflows.

Primary Goal

Keep platform behavior predictable, auditable, and easy to implement across Guest, Partner, Creator, Admin, API, and payment services.

Core Approach

Use backend-controlled state transitions, stored booking snapshots, explicit conditions, and automated scheduled jobs.

2. Scope & Limitations

Scope

  • Accommodation bookings made through BOMO.
  • Guest booking and cancellation workflows.
  • BOMO Collect and Property Collect payment handling.
  • Refund, Partner payout, and Creator payout rules.
  • Video/photo review eligibility and moderation.
  • Backend status, conditional, validation, API, job, and audit rules.

Limitations

  • No property check-in or check-out workflow is required.
  • Property operations, housekeeping, PMS internals, and OTA sync are outside this cookbook.
  • Bank, wallet, card, and gateway posting time is controlled by external providers.
  • Tax, withholding, contract, and local-law requirements may override platform defaults.
  • Rates, fees, commissions, rewards, and clearance periods must be configurable.

3. Development Rules

01
Backend owns status.

Frontend requests actions. It must not directly set final booking, refund, payout, or review states.

02
Use a state machine.

Allow only defined transitions. Reject invalid status jumps.

03
Snapshot confirmed terms.

Store price, fees, cancellation rule, taxes, payment model, and key payout inputs at booking confirmation.

04
Use idempotency.

Booking confirmation, payment capture, refund, webhook, reward creation, and payout must be safe to retry.

05
Protect inventory atomically.

Availability validation and inventory reservation/decrement must be transactional or lock-safe.

06
Money is exact.

Use DECIMAL or integer minor units. Never use floating-point values for money.

07
Use property-local time.

Stay dates, cancellation cutoffs, and automatic completion use the property's timezone.

08
Audit every financial action.

Record actor, action, previous state, new state, amount, reason, source, and timestamp.

09
Provider webhooks are verified.

Verify signatures and never trust browser-return payment success as final proof.

10
Jobs are retry-safe.

Automatic completion, refund sync, reward issuance, and payout batching must tolerate retries without duplicates.

5. Booking Workflow

Select Room & Dates→Validate→Price Snapshot→Payment / Guarantee→Issue Reference→CONFIRMED→Auto COMPLETED

Required Validation

  • Property and room are active and bookable.
  • Arrival date is before stay end date.
  • Occupancy fits room/rate rules.
  • Requested quantity is available for every stay date.
  • Rate plan is active for the dates.
  • Final price is recalculated by backend.
  • Payment/guarantee requirement is satisfied.

Confirmation Rule

  • Create booking reference only after validations pass.
  • Store the final commercial snapshot.
  • Reserve/decrement inventory in the same protected transaction.
  • Send confirmation only after the booking is CONFIRMED.
  • Never require check-in or check-out status.

Booking Conditions

IF inventory is unavailable       → reject booking
IF backend price != client price  → return refreshed quote
IF required payment fails         → keep PENDING or cancel pending attempt
IF payment/guarantee succeeds     → issue reference and CONFIRMED
IF stay_end_at has passed AND status = CONFIRMED
                                  → COMPLETED by scheduled job

Auto-Completion Job

Run on a schedule. Select CONFIRMED bookings where the property-local stay end time has passed. Update to COMPLETED using an idempotent batch. Financial disputes may hold payout without changing the booking completion result.

6. Cancellation Workflow

Cancel Request→Load Stored Policy→Calculate Fee / Refund→Show Result→Guest Confirms→CANCELLED→Refund if Due

Rules

  • Use the cancellation policy snapshot stored at confirmation.
  • Do not recalculate using a newly edited Property policy.
  • Show fee and refundable amount before final confirmation.
  • Cancellation and inventory release must be atomic.
  • A completed or already cancelled booking cannot be cancelled again.

Property Cancellation

  • Guest should not receive a cancellation penalty when the Property cannot honor the booking.
  • For BOMO Collect, create the eligible refund flow.
  • For Property Collect, record the Property refund responsibility.
  • Return inventory when appropriate.
IF status != CONFIRMED           → reject normal cancellation
IF cancellation cutoff applies   → compute stored-policy fee
IF refundable_amount > 0         → create refund instruction
IF refundable_amount = 0         → cancel with no refund
ALWAYS                            → save calculation snapshot + audit

8. Partner Payout Workflow

BOMO Collect→Booking COMPLETED→Clearance→Reconcile→ELIGIBLE→Payout Batch→PAID

Eligibility

  • Payment model is BOMO_COLLECT.
  • Booking is COMPLETED.
  • Required clearance period has passed.
  • No unresolved refund/chargeback condition requires hold.
  • Partner payout account is verified.

Net Payout

Guest payment
- BOMO commission
- payment charges
- refunds / chargebacks
- taxes / withholding
± approved adjustments
= Net Partner payout

Property Collect: do not create an accommodation payout from BOMO because the Property collected the booking payment directly.

9. Creator Payout Workflow

Eligible Earning→Validate Source→Clearance→Available Balance→Payout Batch→PAID

Earning Sources

  • Approved video/photo review reward.
  • Eligible Creator promo-code reward.
  • Other Admin-approved Creator programs.

Eligibility Guard

  • Source booking exists and satisfies program conditions.
  • Booking is not cancelled or fully refunded.
  • Required review or promo event is approved/validated.
  • Creator identity and payout method are verified.
  • Earning has not already been paid or reversed.
IF earning source invalid         → reject earning
IF booking cancelled/full refund  → reverse or block earning
IF clearance not reached          → PENDING
IF verification missing           → ON_HOLD
IF all guards pass                → ELIGIBLE

10. Video / Photo Review Workflow

Upload→Booking & File Validation→Moderation→Approve / Revise / Reject→Publish→Reward Check

Content Rules

  • Review must relate to a genuine eligible BOMO stay.
  • Media must represent the actual experience and must not create a false impression.
  • Reject unlawful, abusive, sexually explicit, dangerous, or unrelated promotional content.
  • Do not expose private personal information.
  • Third-party identity/privacy concerns require moderation or revision.

Development Rules

  • Validate MIME type, extension, size, duration/dimensions, and upload completion server-side.
  • Store original/private media separately from published derivative media where practical.
  • Moderation status and reward eligibility are separate fields.
  • Publishing a review must not automatically create duplicate rewards.
  • All moderation actions require actor and reason logging.
BOMO review-credit default: one completed stay may issue one reward-eligible review credit for the same stay/property. Keep credit expiry configurable; a 90-day expiry is a practical default.

13. Minimum Data to Persist

Booking

id, reference, property, room/rate plan, guest, stay dates, timezone, occupancy, qty, booking status, payment model, commercial snapshot, cancellation snapshot, created/confirmed/completed timestamps.

Payment / Refund

provider refs, amount/currency, payment status, refund status, refundable balance, gateway event IDs, refund refs, reason, actor, timestamps.

Payout Ledger

beneficiary type/id, source booking/earning, gross, deductions, net, hold reason, eligibility date, batch ID, provider reference, payout status.

Review

booking, creator/guest, review type, media object keys, moderation status, publish status, eligibility/reward refs, moderation reason, timestamps.

Audit

entity type/id, action, before/after state, actor type/id, request ID, source IP/device metadata where appropriate, timestamp.

Settings

cancellation templates, payout clearance, commissions/fees, creator reward rules, review credit expiry, upload limits, provider mappings.

15. RBAC, Audit & Security

  • Guest: can quote, book, view own bookings, preview own cancellation, cancel eligible own booking, submit eligible reviews.
  • Partner: can view/manage own inventory and bookings, record NO_SHOW when authorized, view own payout ledger, report Property Collect refund status.
  • Creator: can submit eligible review media and view own earning/payout ledger.
  • BOMO Support: can inspect workflows and perform explicitly granted support actions.
  • Finance: can approve/refconcile refunds and payout batches according to RBAC.
  • Admin: controls settings and exceptional adjustments with mandatory audit reason.
Rule: financial and final-state actions must be permission checked server-side. UI visibility is not authorization.

17. Admin Configuration

Must Be Configurable

  • Cancellation templates and cutoffs.
  • Partner payout clearance and schedules.
  • Creator reward types, rates, minimum payout, and clearance.
  • Commission, payment charge, tax, and adjustment rules.
  • Review credit expiry and reward eligibility.
  • Upload size/type/duration limits.

Change Safety

  • New settings affect new transactions unless explicitly designed otherwise.
  • Existing confirmed bookings use stored snapshots.
  • High-impact finance settings require audit trail and preferably approval workflow.
  • Settings changes must carry effective timestamp and actor.

18. Definition of Done

  • All statuses use guarded transitions.
  • Booking confirmation is transaction-safe and idempotent.
  • Cancellation uses stored confirmed policy terms.
  • Refunds cannot exceed the successful paid balance.
  • BOMO Collect and Property Collect responsibilities are separated.
  • Partner and Creator payout ledgers are independently auditable.
  • Review moderation is separate from reward eligibility.
  • Automatic completion requires no check-in/check-out workflow.
  • Webhooks, jobs, refunds, rewards, and payouts are retry-safe.
  • RBAC and audit logs are enforced on the backend.
  • Acceptance tests pass before production release.
